# cursos

Plataforma de cursos da Profills. Monorepo Bun + Turborepo gerado pelo Better T Stack (`bts.jsonc` guarda o comando de origem; `bunx create-better-t-stack@latest add` acrescenta addons).

Stack: Next.js 16 (App Router, React Compiler, `typedRoutes`), tRPC 11 + TanStack Query, Drizzle 1.0 RC sobre Postgres do Supabase, Clerk para auth, shadcn (estilo `base-lyra`, Base UI), Biome via Ultracite, varlock para env, deploy na Vercel.

## Mapa

O pedido do browser percorre as camadas nesta ordem. Cada linha diz o que o arquivo possui.

### `apps/web` (Next.js, porta 3001)

- `src/proxy.ts`: `clerkMiddleware()` em todas as rotas, sem regra por caminho. No Next 16 o `middleware.ts` virou `proxy.ts`. O `createRouteMatcher` está depreciado no `@clerk/nextjs` 7: a proteção mora em `src/server/api.ts`.
- `src/app/`: rotas. `layout.tsx` monta `ClerkProvider` (com o `appearance` escuro) e `Providers`, com `lang="pt-BR"` e `class="dark"` fixos no `<html>`; `page.tsx` redireciona para `/meus-cursos` até o Início existir; `api/trpc/[trpc]/route.ts` é o único endpoint HTTP da API, e recusa com 403 o `multipart/form-data` cujo `Origin` não seja `CORS_ORIGIN` (`lib/origem.ts`), porque esse corpo não passa por preflight. O `onError` dele (`lib/erro-interno.ts`) registra no log do servidor todo `INTERNAL_SERVER_ERROR`, com caminho e causa, porque o adaptador fetch do tRPC não registra nada.
- `src/app/(aluno)/`: páginas do aluno. `layout.tsx` monta a sidebar e o topo e lê o resumo; `error.tsx` é o erro das páginas do grupo; `meus-cursos/` tem `page.tsx` e `loading.tsx`; `trocar-pontos/` tem os dois e um `error.tsx` próprio, com o título da tela; `cursos/[slug]/page.tsx` é o stub do player.
- `src/app/(admin)/admin/`: área do admin. `layout.tsx` chama `exigirAdmin()` (quem não é admin vê a 404 do app) e monta a sidebar do admin; `error.tsx` é o erro do grupo; `page.tsx` também chama `exigirAdmin()`, porque layout e página rodam em paralelo, e redireciona para `alunos/`. `alunos/page.tsx` busca pessoas no Clerk por um `next/form` com `q`, que navega no cliente; `alunos/loading.tsx` é o esqueleto da busca e do acesso; `alunos/[userId]/page.tsx` mostra as liberações da pessoa e libera ou revoga (404 para userId fora do formato, ou para quem o Clerk não conhece e nunca teve liberação). `catalogo/` lista trilhas e cursos, com o link de cada curso para o editor e o "Novo curso". `catalogo/cursos/novo/page.tsx` gera o id do curso novo e redireciona para `catalogo/cursos/<id>?novo=1`; `catalogo/cursos/[id]/page.tsx` abre o editor por `abrirOuRascunho` e passa `key` pela versão, para o refresh depois de salvar remontar o editor com o documento do banco; tem o próprio `loading.tsx`. `comunicados/` publica, edita e apaga comunicados, com o próprio `loading.tsx`.
- `src/server/api.ts`: `server-only`. `carregarPainel`, `carregarResumo` e `carregarPainelDeTroca` chamam o router no processo por `createCaller`, com `React.cache` por request. O contexto faz `auth.protect()` (quem não tem sessão vai para o login) e passa por `contextoDe`, a mesma leitura de papel do `route.ts`. `exigirAdmin()` é a primeira porta do admin e dá `notFound()` para quem tem sessão sem o papel; `souAdmin()` mostra o link "Área do admin" na sidebar do aluno; `carregarCatalogo`, `carregarCurso`, `carregarPessoas`, `carregarAcessoDoAluno` e `carregarComunicados` passam por `exigirAdmin`. Server Component busca dados por aqui, não pelo cliente de `utils/trpc.ts`.
- `src/context.ts`: cria o contexto do tRPC por request. Valida o token do Clerk com `authenticateRequest`, aceitando só `authorizedParties: [ENV.CORS_ORIGIN]`, e entrega `contextoDe(estado.toAuth(), servicos)`.
- `src/services.ts`: os `servicos` do app, montados uma vez: o `db`, as `capas` (`capasDoSupabase` com `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY`, senão `capasDesligadas`, que recusa todo envio) e as `pessoas` (o Clerk como diretório). O mesmo `clerk` daqui valida o token em `src/context.ts`. Uma regra `noRestrictedImports` do `biome.jsonc` cerca o banco: só este arquivo importa `@cursos/db`, e só `src/context.ts` e `src/server/api.ts` importam `@/services`. Um Server Action lê e grava pelo caller de `server/api.ts`.
- `src/env.server.ts`: ponto de entrada server-only do env. Código de servidor importa `ENV` daqui; `src/env.ts` é gerado.
- `src/utils/trpc.ts`: cliente tRPC + `queryClient`. Manda `Authorization: Bearer <token do Clerk>` em todo request, no browser pelo getter de `utils/clerk-auth.ts` e no servidor por `auth()`. Vão sem lote o `aula.registrar` (com `keepalive`) e toda entrada que não é JSON (`isNonJsonSerializable`), como o `FormData` de `admin.catalogo.salvarCurso`.
- `src/components/providers.tsx`: React Query, `Toaster theme="dark"` e o `ClerkApiAuthBridge`, que registra o `getToken` do Clerk para o cliente tRPC. O app tem um tema só, escuro, sem `ThemeProvider`.
- `src/components/casca/`: o que as áreas do aluno e do admin dividem. `nav-principal.tsx` recebe a lista de itens, link ou "Em breve", com o ícone como elemento (`<House />`), e marca o `aria-current` pelo prefixo da rota; `partes-da-sidebar.tsx` tem a marca e o link do rodapé das duas sidebars; `tela-de-erro.tsx` é a tela dos `error.tsx`; `botoes.ts` tem as classes `BOTAO` e `BOTAO_CONTORNO` dos botões em pílula e `PEQUENO`, o tamanho de 36 px. `src/components/aluno/`: sidebar do aluno, com a lista do menu dela, e topo. `src/components/admin/`: sidebar do admin, com a lista do menu dela; `partes.tsx` (seção, vazio, classes de tabela, de campo, `ICONE` e `AVISO` das telas do admin); `visao-do-catalogo.tsx`; o que os editores de documento dividem: `aviso-de-versao-mudou.tsx` (o aviso de `versao_mudou` com "Recarregar") e `erros-do-editor.tsx` (o contexto com a mensagem por id de input, `useErroDoCampo` e `ErroDoCampo`); o editor do curso: `editor-do-curso.tsx` (o formulário inteiro, com `noValidate`, e a barra de salvar, que manda o documento e a capa numa chamada; no salvar recusado na tela, marca e foca o primeiro campo, e o que não tem campo vira frase na barra), `rascunho-do-curso.ts` (o `RascunhoDoCurso`, com duração, vídeo, número do módulo e preço em texto; `lerRascunho` converte em `DocumentoDoCurso` ou numa lista de problemas, cada um com o id do input ou como frase; os `ler*` dos campos lidos), `estado-do-editor.ts` (o reducer puro `mudar` sobre o rascunho, com teste), `modulos-do-curso.tsx` (módulos e aulas, com Subir, Descer, Mover para e Remover; aula assistida não oferece Remover), `campo-lido.tsx` (`CampoDeTexto` e `CampoLido`, o campo de texto que vira outro tipo) e `campo-de-capa.tsx` (confere tipo, tamanho e medida antes de enviar, com prévia); `lista-de-pessoas.tsx` e `foto-da-pessoa.tsx` da busca; `acesso-do-aluno.tsx`, que libera e revoga com um `useAcao` por linha e só lê o que o servidor derivou (`acao`, `liberado`, `trocadosNaTrilha`, `emProducao`, `pelaTrilha`); a tela guarda só qual linha está confirmando. Liberar trilha manda os ids de `trocadosNaTrilha` como `trocadosVistos`. Depois de liberar, o foco vai para o selo "Liberado" da linha; depois de revogar, para o título "Liberações". `confirmacao-na-linha.tsx` é a confirmação dentro da linha (revogar; liberar trilha com curso trocado), que fecha com Escape e devolve o foco ao botão que a abriu. `comunicados.tsx` tem o formulário de novo comunicado e a lista, em que editar abre o mesmo formulário dentro do item e apagar usa a `ConfirmacaoNaLinha`; o id do comunicado novo nasce no formulário, e um id novo o remonta vazio depois de publicar. `src/components/meus-cursos/`: as peças da tela; `conteudo.tsx` monta a página a partir do painel e do resumo. `src/components/trocar-pontos/`: saldo, grade de cursos com a confirmação no card, e extrato; `cartao-de-troca.tsx` chama `troca.trocar` pelo `useAcao` e move o foco; `cursos-para-trocar.tsx` guarda só quem está confirmando, o aviso e o destaque do extrato.
- `src/lib/formato.ts`: números, pontos com sinal, minutos, datas, o "quando" do extrato, plural em pt-BR e `duracaoDoTexto` ("mm:ss" ou "h:mm:ss" do editor para segundos). As peças dos editores de documento (curso e trilha): `abrir-ou-rascunho.ts` (o que a página `[id]` abre: o banco vence, `?novo=1` só vale para id que não existe, id fora de `z.uuid()` é 404), `use-salvar-documento.ts` (`useSalvarDocumento`, com `pendente`, `versaoMudou`, `recarregar` e o `router.replace` do documento novo; `telaDepoisDeSalvar`, a decisão pura; `useTituloComFoco`, o h1 que recebe o foco quando o editor remonta), `use-guarda-de-saida.ts` (o `beforeunload` com mudança não salva) e `editor.ts` (`focarDepois` e `novoId`). A largura e a altura da capa vêm do banco (`curso.capa_largura` e `capa_altura`), dentro de `curso.capa`.
- `src/lib/use-acao.ts`: `useAcao`, o caminho de toda mutação que a pessoa dispara. Roda a chamada do `trpcClient` numa transition, mostra em toast só a mensagem que o servidor marcou com `paraAPessoa` (o resto ganha um texto genérico) e termina em `router.refresh()`, com sucesso ou recusa do servidor. Não recarrega em `versao_mudou` (o editor perderia o rascunho) nem em erro de rede (o refresh sem servidor vira navegação de página inteira). `aoRecusar(motivo)` entrega o `Motivo` da recusa, lido por `isTRPCClientError<AppRouter>`, para a tela marcar o campo ou o aviso. `rodarAcao` é o corpo dele sem React, e é o que o teste exercita. A exceção é o player (`lib/player/use-player-da-aula.ts`), que sincroniza o progresso em segundo plano, sem toast e sem recarregar; `use-acao.test.ts` falha se outro arquivo de `src/` chamar `.mutate(` sem o `useAcao`, e a lista de exceções diz o motivo de cada uma.
- `next.config.ts`: plugin do varlock por fora, PWA (`pwa.config.ts`) por dentro. Com `SUPABASE_URL` no ambiente do build, `images.remotePatterns` libera a URL pública do bucket `capas` para o `next/image`.

### `packages/api` (`@cursos/api`)

- `src/index.ts`: `router`, `publicProcedure`, `protectedProcedure` e `adminProcedure`. O protegido lança `UNAUTHORIZED` sem sessão e estreita `ctx.auth` para `Sessao`. O do admin lança `FORBIDDEN` para quem não tem papel `admin` e entrega `ctx.admin` (`AdminId`), que só ele fabrica. Ele passa por `traduzErroDoBanco`, que troca a violação de restrição que tem frase em `consultas/erros.ts` por um `ErroParaAPessoa`. `ErroParaAPessoa` é a recusa com mensagem escrita para a pessoa, em pt-BR; o `errorFormatter` marca `data.paraAPessoa` nela, e só essa mensagem chega ao toast. Recusa de negócio sai sempre por ela: `index.test.ts` falha se outro arquivo de `src/` fizer `new TRPCError(`. O `errorFormatter` também põe `data.motivo` (`Motivo`: `versao_mudou`, `slug_repetido`, `codigo_repetido`, ou `null`), que a tela lê para decidir sem ler o texto; o nome do motivo é contrato com o cliente.
- `src/routers/index.ts`: `appRouter` (`admin.catalogo.{visao, abrirCurso, salvarCurso, apagarCurso}`, `admin.alunos.{buscar, acesso, liberar, revogar}`, `admin.comunicados.{lista, salvar, apagar}`, `meusCursos.painel`, `aluno.resumo`, `aula.*`, `troca.painel`, `troca.trocar`, `healthCheck`) e `createCaller`. Router novo entra aqui como chave. `routers/admin.ts` usa só `adminProcedure`, e `admin.test.ts` percorre todo `admin.*` sem sessão e com aluno.
- `src/dominio/`: regras puras, sem banco e sem relógio próprio: estado do curso, sequência em dias úteis, retomada e a montagem do painel. `pontos.ts` transforma lançamento em linha do extrato e monta "Como ganhar pontos"; `troca.ts` decide quem pode trocar (`situacao`, usada pela tela e pela mutação), monta os cards e decide a troca; `catalogo.ts` tem os tipos da visão do catálogo do admin, que a tela importa; `liberacao.ts` decide liberar (idempotente) e monta a tela de acesso, e `acaoNaLiberacao` é a única regra de "revogável", que a tela e o `revogar` usam; `edicao-do-curso.ts` tem o `DocumentoDoCurso` (schema zod, que o editor e o servidor usam, e que devolve o documento na forma do banco: módulos por número, níveis por ordem, ids em minúscula), o `FormData` de `salvarCurso`, `edicaoDeCursoNovo` e `FORMATO_DO_SLUG`, o formato que o campo do editor confere; `capa.ts` tem os limites da capa (`LIMITE_DA_CAPA`, `recusaDoTamanho`, `recusaDaMedida`), que o editor também importa; `plano-do-curso.ts`, só do servidor, tem `planejarCurso`, que decide o que some, se pode sumir e a versão que fica, e `versaoDoCurso`, que inclui a URL da capa; `versao.ts` deriva a versão de um documento do conteúdo (sha256 de `node:crypto`, só no servidor); `video.ts` tem `videoDoTexto`, que lê o id ou o link do YouTube colado pelo admin; `comunicado.ts` tem os tipos da tela de comunicados, os limites de título e texto que o router e o formulário dividem, e põe o nome do Clerk em quem publicou; `tipos.ts` deriva `StatusDoCurso` e `OrigemDaLiberacao` das listas de `@cursos/db/schema/formatos`, sem repetir os literais. Testes com `bun test`.
- `src/consultas/`: as consultas do painel (5 statements) e do resumo (2), em paralelo, e o teste de integração no banco local. `trava.ts` tem as travas de transação: `comAlunoTravado` entrega um `AlunoTravado` (`tx` e `userId` juntos), e todo débito de pontos e toda escrita de liberação rodam dentro dela. O crédito de `aula.registrar` não trava: ele só soma e não deixa o saldo negativo. `pontos.ts` é a fonte única de saldo e semana (`linhasDoSaldo`), do extrato e de `comSaldoTravado` (a trava do aluno mais o saldo): todo débito passa por ela. `liberacao.ts` é o único escritor de `liberacao`: `inserirLiberacao` (o único INSERT, de origem `admin` ou `troca`), `liberar` (recebe a `Pessoa` de `porId`, então só libera para quem o Clerk conhece) e `revogar`, as duas com o aluno travado, e `linhasDoAcesso` para a tela. Revogar grava `greatest(agora, liberada_em)`. Dentro da transação as consultas rodam em série, nunca em `Promise.all`. `liberacao.test.ts` falha se outro arquivo de `src/` fizer `insert(liberacao)`; `liberacao.integration.test.ts` prova a corrida entre liberar trilha e trocar, nas duas ordens, e entre revogar e liberar. `troca.ts` lê o painel de troca e grava a troca (liberação de origem `troca` mais lançamento negativo, na mesma transação). `catalogo.ts` tem a `visaoDoCatalogo` do admin. `comunicado.ts` é o único escritor de `comunicado`: `salvarComunicado` é upsert pelo id que nasce no formulário (reenviar não duplica), grava `publicado_por` com o `AdminId` e, ao editar, mantém `publicado_em` e `publicado_por`; `apagarComunicado` devolve `{ apagado: false }` para o que já não existe. O leitor do aluno continua sendo o statement 5 de `linhasDoPainel`. `edicao-do-curso.ts` é o único escritor de curso, nível, módulo e aula: `salvarCurso` sobe a capa fora da transação, trava `curso:<id>` e grava o documento inteiro em ordem fixa (`gravarCurso`), que desloca números de módulo e posições de aula para acima do teto antes do upsert dos finais, porque `modulo_numero_unico` e `aula_posicao_unica` não são deferrable. O upsert só atualiza linha do próprio curso, e a contagem do `returning` recusa id de outro curso. `apagarCurso` traduz a FK que escapa da conta de uso para `CURSO_EM_USO`. `erros.ts` liga nome de unique e check a mensagem (`MENSAGEM_DA_RESTRICAO`) ou põe a restrição em `SEM_MENSAGEM_PROPRIA`; FK fica sempre fora da tabela, porque dispara nos dois sentidos. `erros.integration.test.ts` confere as duas listas contra o banco nos dois sentidos.
- `src/externos/capas.ts`: a porta do Storage. `lerCapa` decide formato e medida pelos bytes (`image-size`), com as regras de `dominio/capa.ts`, e nomeia pelo sha256; `capasDoSupabase` recusa o arquivo pesado pelo `size` antes de ler, envia ao bucket público `capas` pela API REST com a chave service role e manda o corpo de erro do Storage ao log, não ao cliente.
- `src/context.ts`: `Sessao`, `Papel`, `ehAdmin(sessao)`, `Servicos`, `Context` e `contextoDe`, a única leitura de `sessionClaims` do app. O claim `papel` vem do session token do Clerk (`{{user.public_metadata.papel}}`); ausente, `null` ou outro texto vale `aluno`. Compare papel por `ehAdmin`, não por `=== "admin"`. `src/contexto-de-teste.ts` monta o `Context` dos testes, com um Clerk falso (`pessoasDeTeste`) que conhece só as pessoas que o teste passa.
- `src/externos/pessoas.ts`: a porta `Pessoas` (`buscar(termo)` por nome, e-mail ou userId, que devolve até 20 pessoas e o total que casou; `porId`), sobre a Backend API do Clerk. O tipo `User` do SDK não sai deste arquivo; o resto vê `Pessoa` (`dominio/tipos.ts`).
- `src/sessao.ts`: a marca de tipo da `Sessao` e `sessaoDe`, o único lugar que a põe. O arquivo fica fora dos `exports`, então só `contextoDe` e `contextoDeTeste` criam uma sessão: `createCaller` com uma sessão montada à mão, ou com `papel: "admin"` espalhado sobre uma sessão de aluno, não compila. A cerca barra o atalho, não o código hostil: `contextoDe` com claims montados à mão e um `as Context` ainda compilam.
- `package.json` fecha os `exports`: o app importa só `.`, `./context`, `./dominio/*`, `./externos/capas` e `./externos/pessoas` (as duas para `services.ts`) e `./routers/index`. `consultas/` não sai do pacote.

### `packages/db` (`@cursos/db`)

- `src/schema/`: catálogo, acesso, estudo, pontos e comunicado; `index.ts` exporta tudo e `drizzle.config.ts` lê só esse arquivo e só o schema `public`. Toda tabela usa `snakeCase.table` (chave camelCase, coluna snake_case). `formatos.ts`, sem import, guarda as listas dos enums (`STATUS_DO_CURSO`, `ORIGEM_DA_LIBERACAO`) para o browser ler sem levar o `drizzle-orm`; `comum.ts` monta os `pgEnum` a partir delas. `restricoes.integration.test.ts` prova cada constraint, e `migracao.integration.test.ts` aplica as migrações sobre linhas plantadas antes de cada uma.
- `src/relations.ts`: relations v2 do Drizzle 1.0 (`defineRelations(schema)`), passadas ao `drizzle()` em `src/index.ts`. A API de relations v1 (`relations()` por tabela) não vale nesta versão.
- `src/migrations/`: saída do `db:generate`. `drizzle.local.config.ts` aponta só para o Supabase local e não lê o `.env`.
- `src/seed/`: seed de exemplo. `guarda-local.ts` recusa host que não seja o Supabase local; `--cloud` exige `--sim-cloud`. O seed só planta curso e trilha que faltam: o que já existe é do admin, e mudar `dados.ts` de um curso existente pede um banco local limpo. Os fatos dos alunos de exemplo, liberações inclusive, são apagados e recriados por `user_id`. `index.integration.test.ts` prova as duas execuções.
- `supabase/config.toml`: stack local do Supabase CLI (`project_id = "cursos"`, portas entre 54320 e 54329; o banco fica na 54322).

### `packages/ui` (`@cursos/ui`)

- Todos os componentes de UI do registro `@shadcn` (estilo `base-lyra`) já estão em `src/components/`, exceto `toast` (o app usa o `sonner`) e `direction` (só RTL). Hooks em `src/hooks/`, `cn` em `src/lib/utils.ts`, tokens em `src/styles/globals.css`. Importe por caminho: `@cursos/ui/components/button`.

## Env (varlock)

- O contrato fica em `apps/web/.env.schema`; os valores locais, em `apps/web/.env` (fora do git). `packages/db/.env.schema` importa `NODE_ENV` e `DATABASE_*` do app.
- `@defaultSensitive=true` marca toda variável como segredo. Valor que chega ao browser leva `@public`, senão o varlock acusa `DETECTED LEAKED SENSITIVE CONFIG` e derruba o request. Foi o que aconteceu com `CLERK_PUBLISHABLE_KEY`.
- Depois de editar o schema: `bun run env:generate` para regenerar os `env.ts`, e reinicie o `next dev`.
- `SUPABASE_URL` (`@public`, porque a URL da capa leva o host ao browser) e `SUPABASE_SERVICE_ROLE_KEY` são opcionais. Sem uma delas, o envio de capa do admin recusa com "não configurado" e o resto funciona.
- `CORS_ORIGIN` precisa ser exatamente a origem do browser (`http://localhost:3001` no dev). Com outro valor, o Clerk recusa o token e todo `protectedProcedure` responde `UNAUTHORIZED`.

## Banco

- O `DATABASE_URL` do `.env` aponta para o projeto **cloud** do Supabase (`lsatugtpqwiylnfutolg`, org profillsbrasil, `sa-east-1`), pelo pooler de transação na porta 6543. É decisão do dono: o dev usa o banco real. Trate `db:push` e `db:migrate` como escrita em produção e confirme antes.
- `drizzle-kit` contra o cloud usa o mesmo host na porta 5432 (session pooler).
- O app conecta como `postgres`, que tem `BYPASSRLS`. O projeto cloud tem o event trigger `ensure_rls`, que liga RLS em toda tabela nova do `public`, e a Data API não expõe tabelas novas. RLS só protege acesso via `anon`/`authenticated`; a autorização do app mora nos procedures do tRPC.
- O Supabase local (`bun run db:start` / `db:stop`) existe para testes isolados; para usá-lo, troque o `DATABASE_URL` para `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.
- `bun run db:push` (e `db:generate`, `db:migrate`) da raiz é task interativa do turbo e falha num shell sem TTY. Num agente, rode `bunx drizzle-kit <comando>` dentro de `packages/db`.
- O MCP `supabase` deste ambiente pode estar logado em outra conta e não enxergar o projeto. Confira com `list_projects` antes de usá-lo; se o projeto não aparecer, use o dashboard.

## Auth (Clerk)

- App "cursos" na workspace PROFILLS DO BRASIL, só a instância Development (`pk_test`/`sk_test`). A instância de produção exige domínio próprio.
- Usuário logado no servidor: `ctx.auth.userId` dentro de `protectedProcedure`. Não existe tabela de usuários; quando precisar, sincronize pelo webhook do Clerk (skill `clerk-webhooks`).
- Papel de admin: `{ "papel": "admin" }` no Public metadata do usuário, e o claim `{ "papel": "{{user.public_metadata.papel}}" }` em Sessions, "Customize session token". Quem muda o metadata precisa sair e entrar de novo, ou esperar o token renovar (até 60 s).

## Comandos

- `bun run dev` sobe tudo; `bun run dev:web` só o app. `bun run --cwd apps/web dev:local` sobe o app contra o Supabase local (o `process.env` vence o `.env` no varlock). Não use `bun --bun next dev`: o Turbopack não resolve o `pg` no runtime do Bun.
- Testes: `bun run test`. Os de integração só rodam com `TEST_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres` e recusam host que não seja local. Banco local: `bun run db:migrate:local` e `bun run db:seed -- --aluno user_xxx`, dentro de `packages/db`.
- Antes de commitar: `bun run check-types` e `bun x ultracite check` verdes. Um hook do Claude Code (`.claude/hooks/formatar-arquivo-editado.ts`) roda o Biome no arquivo editado depois de cada Edit/Write, então o arquivo pode mudar logo após a edição: releia antes do próximo Edit.
- Deploy: `bun run deploy:setup` linka a Vercel. `bun run env:production` sem argumento envia o `apps/web/.env`, que tem as chaves `pk_test` e o banco do dev. Para produção, monte um `apps/web/.env.production.local` (já ignorado pelo git) e rode `bun run env:production apps/web/.env.production.local`.

## Código

Biome (via Ultracite) cobre formatação e a maior parte do estilo. O que ele não pega:

- Busca assíncrona de dados vai em Server Component, não em Client Component `async`.
- Erro para o usuário sai como `ErroParaAPessoa` com `code` e `message`; o `queryClient` já mostra toast em qualquer erro de query.
- Use o vocabulário do `GLOSSARY.md` em nomes de tabela, procedure e componente.
- Constante de classe não mora em módulo "use client": num Server Component ela chega como client reference, e o `cn` a descarta sem erro. Ela vai para um módulo sem a diretiva (`casca/botoes.ts`, `admin/partes.tsx`); `components/fronteira-do-cliente.test.ts` acusa a volta.

## Agent skills

### Issue tracker

As issues ficam no GitHub Issues de `profillsbrasil/cursos` (repo público). Use o `gh` dentro do clone, que já infere o repo.

- Criar: `gh issue create --title "..." --body "..."` (heredoc para corpo de várias linhas).
- Ler: `gh issue view <n> --comments`.
- Listar: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'`, com `--label` e `--state` conforme o caso.
- Comentar: `gh issue comment <n> --body "..."`.
- Labels: `gh issue edit <n> --add-label "..."` / `--remove-label "..."`. Exige permissão de triage no repo; as contas do gh desta máquina hoje têm só leitura, então essa chamada falha até o dono dar acesso.
- Fechar: `gh issue close <n> --comment "..."`.
- "Publicar no issue tracker" quer dizer criar uma issue no GitHub. "Buscar o ticket" quer dizer `gh issue view <n> --comments`.
- PRs como superfície de pedidos: **não**. PRs externos não entram na triagem.
- `#42` pode ser issue ou PR (mesma numeração): tente `gh pr view 42` e caia para `gh issue view 42`.

Wayfinding (`/wayfinder`): o **mapa** é uma issue com label `wayfinder:map` e corpo Notes / Decisions-so-far / Fog. Cada ticket filho é sub-issue do mapa (`gh api` no endpoint de sub-issues), ou, sem sub-issues, entra na task list do mapa com `Part of #<mapa>` no topo; label `wayfinder:<research|prototype|grilling|task>`. Bloqueio usa as dependências nativas: `gh api --method POST repos/profillsbrasil/cursos/issues/<filho>/dependencies/blocked_by -F issue_id=<id do bloqueador>`, onde o id é o database id (`gh api repos/profillsbrasil/cursos/issues/<n> --jq .id`); sem dependências, uma linha `Blocked by: #<n>` no topo. Fronteira: filhos abertos do mapa, sem bloqueador aberto e sem assignee, na ordem do mapa. Assumir: `gh issue edit <n> --add-assignee @me`. Resolver: comentar a resposta, fechar e anexar um ponteiro (resumo + link) em Decisions-so-far do mapa.

### Triage labels

Os cinco papéis usam o nome padrão como label: `needs-triage` (o mantenedor precisa avaliar), `needs-info` (esperando quem reportou), `ready-for-agent` (especificado, pronto para um agente sozinho), `ready-for-human` (precisa de implementação humana), `wontfix` (não será feito).

### Domain docs

Contexto único: `GLOSSARY.md` e `docs/adr/` na raiz.

- Antes de explorar uma área, leia o `GLOSSARY.md` e as ADRs de `docs/adr/` que tocam nela. Se não existirem, siga em frente sem comentar; o `/domain-modeling` (via `/grill-with-docs` e `/improve-codebase-architecture`) cria os arquivos quando um termo ou decisão é resolvido.
- Nome de conceito de domínio em issue, proposta, hipótese ou teste usa o termo do glossário. Conceito ausente do glossário é sinal: ou a linguagem é inventada, ou é uma lacuna para o `/domain-modeling`.
- Saída que contradiz uma ADR diz isso explicitamente: _Contradiz a ADR-0007 (...), mas vale reabrir porque..._
